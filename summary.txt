SOCCER MASTER 27 (SM27) — PROJECT SUMMARY
Последнее обновление: 2026-11-22 17:22 UTC
Язык общения и интерфейса: русский.

1. ЦЕЛЬ ПРОЕКТА
SM27 — футбольный менеджер / симулятор карьеры с игровым сезоном 2026/27. Цель — постепенно довести текущий MVP до полноценного, глубокого футбольного менеджера: управление клубом и составом, тактика, матчи, трансферы, развитие игроков, турниры и долгосрочная карьера. Это не статичный макет: интерфейс работает с FastAPI и Neon PostgreSQL.

4. ТЕХНОЛОГИИ И СТРУКТУРА
- Backend: Python 3.12+, FastAPI, Pydantic, psycopg 3 / psycopg_pool.
- Database: Neon PostgreSQL 17. Supabase не используется.
- Frontend: обычные HTML/CSS/Vanilla JavaScript; UI лежит в app/static/index.html, app/static/app.css, app/static/app.js. Не добавлять фреймворк frontend без отдельного обоснования.
- Основные файлы:
  app/main.py — API, бизнес-логика карьеры, каталог, состав, тактика, календарь, симуляция и переход сезона.
  app/auth.py — PBKDF2-SHA256 (310 000 итераций), хеширование session token, HttpOnly cookie.
  app/config.py — env settings.
  app/db.py — пул до 4 подключений, reconnect/keepalive, запуск SQL-миграций.
  app/engine.py — round-robin, рейтинг/потенциал и футбольная симуляция.
  app/schemas.py — Pydantic API-схемы и whitelist схем построения.
  app/data_policy.py — проверка повторного использования лицензированных данных.
  scripts/import_catalog.py — загрузка/обработка каталога.
  sql/001_sm27_migration.sql — основная additive/idempotent миграция.
  sql/002_sm27_squad_tactics.sql — поля профиля игроков и рейтинги клубов.
  sql/003_sm27_existing_career_backfill.sql — безопасное заполнение полей существующих карьер.
  tests/ — тесты игровой логики, профилей игроков и data policy.
  .github/workflows/ci.yml — проверки Python, pytest и JS syntax.
  .github/workflows/import-catalog.yml — ручной импорт каталога через GitHub Actions.
  render.yaml — Render Blueprint.
- Публичные API-группы: /api/health; auth register/login/logout; /api/me; catalog summary/leagues/clubs; saves create/restart; dashboard; squad; tactics GET/PUT; fixtures; game/advance; standings; data-status.

5. ТЕКУЩИЙ ИГРОВОЙ MVP
- Регистрация/вход менеджера, отдельное сохранение карьеры, выбор клуба из каталога.
- Игровые копии клубов и составов, календарь лиги double round-robin, таблица, тактика и симуляция тура по кнопке.
- Матчи записывают счёт, xG, владение, удары, удары в створ и события матча; после тура обновляется таблица.
- Тактический экран: футбольное поле, расстановка, стартовые 11, запас, роли/позиционные штрафы, инструкции и сохранение тактики. Поддерживается расширенный список формаций в стиле FC 27.
- Составы: карточки и профили игроков, позиции и вторичные позиции, атрибуты, OVR/potential, возраст, стоимость, зарплата/контракт, форма, мораль, готовность и флаг национальности.
- Автоматический переход между сезонами реализован в последнем merged-наборе изменений.
- Для неполных source squads создаётся игровой состав SM27 с явно помеченными вымышленными игроками академии. Это не реальные футболисты.
- Клубы показываются в алфавитном порядке; официальные display names нормализуются; эмблемы очищаются и имеют fallback.
- MVP ещё не является полной игрой.

11. БЮДЖЕТ РЕСУРСОВ — ОБЯЗАТЕЛЬНО СОБЛЮДАТЬ БЕСПЛАТНЫЕ ТАРИФЫ
Пользователь прямо напомнил 2026-11-22: всех лимитов бесплатных версий Neon, Render и GitHub должно хватать для использования SM27. Это жёсткое требование ко всем будущим решениям.
- Neon: не выполнять polling и повторные запросы без необходимости; не делать N+1; объединять чтение нескольких сущностей для одного экрана в агрегированные API/SQL-запросы; использовать LIMIT и пагинацию; индексировать реальные фильтры/сортировки; не загружать все матчи/игроков без нужды; кэшировать относительно статичный каталог, список лиг и карточки клубов с безопасным TTL/инвалидацией; оперативные данные карьеры (состав, тактика, турнирная таблица, дата/результаты) не отдавать из устаревшего кэша; пакетировать записи и использовать транзакции; запускать тяжёлый импорт каталога вручную и только при необходимости; избегать частых connect/disconnect, сохранять пул до 4 подключений и короткие/контролируемые транзакции; для тяжёлых запросов сначала проверять EXPLAIN/индексы; не выполнять дорогие полные пересчёты при каждом HTTP-запросе.
- Neon: дешёвый Free compute с лимитом 0.25–0.5 CU и авто-suspend — известная текущая конфигурация. 4 соединения — верхний предел пула, а не целевой расход. Держать compute активным только пока обслуживаются реальные запросы.

Учитывать сон Free-инстанса и показывать корректное состояние загрузки/пробуждения.
- Render: документационные коммиты summary.txt не должны без необходимости вызывать повторный deploy/сборку приложения. Проверить реальное поведение autoDeploy и при необходимости использовать безопасный deployment workflow без автоматического rebuild на каждый docs-only commit; кодовые изменения всё равно должны иметь понятный проверяемый способ деплоя. Не менять настройки сервиса без подтверждения workspace и оценки последствий.

- Frontend/backend: не опрашивать API в фоне каждую секунду/минуту; грузить данные при входе на экран и после действий, реально меняющих данные; объединять запросы; ограничивать страницы и объём payload; серверный in-memory TTL cache допустим для неизменяемого/медленно меняющегося публичного каталога, но не для сессионных/финансовых/игровых состояний.
- Не гарантировать работу при произвольной высокой нагрузке: целевая нагрузка — личное использование/малое число менеджеров в рамках бесплатных лимитов. При обнаружении вероятного превышения сначала оптимизировать, ограничить объём/частоту или упростить функционал, а не предлагать платный тариф как решение.
